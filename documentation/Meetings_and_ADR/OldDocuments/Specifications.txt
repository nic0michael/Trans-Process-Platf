# Nico's Java Project

Yes. I read the feedback as a whole rather than treating each test separately.

The strongest project for you is **not just a CRUD application**. It should be a realistic **transaction-processing platform** that deliberately exercises the areas the interviewers identified while also allowing you to demonstrate your existing strengths.

## Recommended project

### **Nico Transaction Processing Platform — NTP**

A Java/Angular application for submitting and processing **customer transactions asynchronously**.

The system will accept transactions through a REST API, validate them, persist them, publish processing events through RabbitMQ, process them asynchronously, prevent duplicate processing, record the result, and expose the status through an Angular dashboard.

It is deliberately designed to demonstrate:

* Java core knowledge
* Spring Boot
* REST
* Angular
* PostgreSQL
* SQL indexes and query optimisation
* RabbitMQ
* asynchronous processing
* Outbox Pattern
* idempotency
* database constraints
* retry and dead-letter processing
* service virtualization
* fault injection
* contract testing
* unit/integration testing
* Docker
* Docker Compose
* observability
* metrics
* logging
* distributed-system thinking
* API validation
* error handling
* concurrency
* HashMap/equals/hashCode concepts
* Kubernetes-ready architecture
* CI/CD-ready structure

This is also a **useful portfolio project**, because it resembles the type of transaction-processing backend found in banking, payments, insurance and other enterprise environments without becoming tied to one particular company.

```text
            RETRY
              |
        +-----+-----+
        |           |
        v           v

```

The state transitions must be controlled.

Invalid transitions must be rejected.

This gives you a good opportunity to use the **State pattern**.

# 10. Idempotency

This is one of the project's major features.

Every request contains:

```text
requestId
```

The database must enforce:

```text
UNIQUE(request_id)
```

If the same request is submitted twice:

```text
Request 1 -> process
Request 2 -> detect duplicate
```

The transaction must **not be processed twice**.

This directly demonstrates one of your existing strengths.

---

# 11. Outbox Pattern

This should be a central architectural feature.

When the transaction is accepted:

```text
BEGIN TRANSACTION

INSERT transaction

INSERT outbox_event

COMMIT
```

The application must never have:

```text
database commit
     +
RabbitMQ publish
```

as two unrelated operations.

The Outbox ensures the event is persisted with the transaction.

Then an Outbox Publisher publishes:

```text
Outbox
   |
   v
RabbitMQ
```

This also gives you another excellent interview discussion topic.

---

# 12. RabbitMQ

RabbitMQ will provide asynchronous processing.

Suggested logical structure:

```text

        |
        +---- transaction.queue
        |
        +---- retry.queue
        |
        +---- dead-letter.queue
```

Messages contain:

```text
transactionId

eventType
timestamp

```

# 13. Retry architecture

A transaction that temporarily fails should not immediately become permanently failed.

Example:

```text
Attempt 1
   |
   v
FAIL
   |
   v
Retry

Attempt 2
   |
   v
FAIL
   |
   v
Retry

Attempt 3
   |
   v
FAIL
   |
   v
DLQ
```

Maximum attempts:

```text
3
```

This should be configurable.

# 14. Dead Letter Queue

# 19. Database indexes

This is deliberately included because of the feedback.

At minimum:

```text

```

Composite indexes should be justified through actual query requirements.

For example:

```text
(customer_id, created_at)
(status, created_at)
(status, customer_id, created_at)
```

But **do not automatically create all of these**.

One of the architecture/design exercises should be:

> Which indexes are actually required and why?

That gives you a concrete interview discussion around composite indexing and query optimisation.
